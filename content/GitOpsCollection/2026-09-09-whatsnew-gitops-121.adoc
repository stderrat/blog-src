Red Hat OpenShift GitOps 1.21 is one of those releases where the headline features are easy to summarise, while the parts that will cost you time are in the sections most of us scroll past: breaking changes and deprecated features. Two of them touch configurations I have described in this series, and one deprecation led to a customer asking me whether sharding had been removed.

It has not. The details are further down.

This article covers what changed, what it means in practice, and which of my own setups need a second look.

GitOps 1.21.0 is available on OpenShift Container Platform 4.14 and 4.16 to 4.22.

NOTE: The z-stream releases narrowed that range. 1.21.1 to 1.21.4 are available on OpenShift Container Platform 4.18 to 4.22. If you run an older OpenShift version, check which z-stream you are entitled to before planning the upgrade.

The step from Argo CD 3.3 to 3.4 matters most, because several new Operator capabilities exist only because Argo CD 3.4 provides the mechanism underneath.

== The three headline features

=== Argo CD Image Updater is generally available

The Image Updater was a Technology Preview since 1.18 and is now GA. It updates container images automatically for workloads managed by Argo CD. You declare which applications and images to track in an `ImageUpdater` custom resource, and the result is written back either through the Argo CD API or into Git. Kustomize and Helm applications are supported.

This closes the gap between CI and CD that I previously bridged with a Tekton task in link:/securesupplychain/2023-06-23-securesupplychain-step8[Step 8 of the Secure Supply Chain series]. It has its own article, including a small test image you can build yourself: link:/gitopscollection/2026-09-06-argocd-image-updater[Ep.17].

Two related changes matter even if you already used the Technology Preview:

* The Image Updater now defaults to namespace-scoped operation. It previously required cluster-wide RBAC. Now it watches only the namespace it is installed in, with namespace-scoped `Role` and `RoleBinding` manifests, and you widen that scope explicitly.
* A pull request workflow was added for the Git write-back method, so image updates can target protected branches through a review instead of a direct push.

=== The Argo CD CLI is generally available

The `argocd` CLI has been a Technology Preview since 1.12 and is now GA, which means a supported binary from Red Hat instead of the upstream release. The `openshift-gitops-argocd-cli` RPM for RHEL 8 and 9 was deprecated back in 1.19. If your pipelines still install the CLI from that RPM, move them to the Content Gateway download.

=== The Argo CD Agent gains a hybrid architecture, Technology Preview

This is the change I find most useful for existing customers. Until now, running the Argo CD Agent principal meant the application controller on the hub had to be disabled, which forced a separate Argo CD instance and an all-or-nothing migration. In 1.21 both can run in the same instance. Traditional applications stay with the hub's application controller, agent applications are pulled by the agents, and both appear in the same UI. Isolation is enforced by label selectors and the `argocd.argoproj.io/skip-reconcile` annotation.

I have written this one up in detail as well: link:/gitopscollection/2026-09-06-argocd-agent-hybrid-architecture[Ep.18].

The agent received a few other improvements in this release: `ServiceMonitor` resources for the principal and agent components, so metrics land in the Console dashboards, optional end-to-end TLS for Redis traffic, and repository credential sync scoped by `AppProject`.

== Smaller features that solve real annoyances

=== Declarative management of Git webhook secrets

Until now, webhook secrets for Git providers had to end up in the Operator-managed `argocd-secret`, which meant either editing an Operator-managed resource by hand or using the External Secrets Operator to inject values into it. In 1.21 the Argo CD custom resource gained a `spec.webhookSecrets` field that references standalone Kubernetes secrets:

.Declarative webhook secret
[source,yaml]
----
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  webhookSecrets:
    github:
      webhookSecretRef:
        name: github-secret # <1>
        key: token # <2>
----
<1> A normal secret in the same namespace, which can be produced by the External Secrets Operator, by Sealed Secrets, or by whatever you already use.
<2> The key inside that secret holding the shared webhook secret.

GitHub, GitLab, Bitbucket Cloud, Bitbucket Server, Gogs and Azure DevOps are supported. Existing manual configurations keep working, so this is backward compatible.

This removes one of the last steps in an otherwise declarative setup that required editing a resource by hand.

=== Web terminal from the Argo CD UI

The web-based terminal can now be enabled through the Operator:

[source,yaml]
----
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  webTerminalEnabled: true
----

CAUTION: In 1.21.0 the terminal tab appears but does not accept input, because the `openshift-gitops-argocd-server` service account lacks permission to create `pods/exec`. The documented workaround is a `ClusterRole` and `ClusterRoleBinding` granting that permission. The missing permissions were fixed in 1.21.1, so upgrading is the better option. Consider what the feature grants before you enable it, because it lets Argo CD users open a shell in any pod the Argo CD server can reach.

=== GitOps Console plugin resource pages, Technology Preview

The Console plugin moved from Developer Preview to Technology Preview. It offers list and detail pages for `Application`, `ApplicationSet`, `AppProject` and `Rollout` resources, filters for health and sync status, ApplicationSet views including progressive sync steps, and links between the OpenShift Console and the Argo CD UI. It requires OpenShift Container Platform 4.19 or later.

=== What Argo CD 3.4 brings along

A few upstream changes you will notice in daily use:

* Glob patterns are allowed for `valueFiles`, for example `/env/*.yaml`, which helps when the override file names are not known in advance.
* Additional filters in the UI, including filtering by annotation and a button to clear all filters.
* The `argocd.argoproj.io/skip-reconcile` annotation on cluster secrets, which is the foundation of the agent hybrid architecture.
* A new `argocd account session-token` command that prints the current session token for use in scripts.

== Breaking changes

=== ApplicationSet tokenRef strict mode is on by default

If `.spec.applicationSet.sourceNamespaces` on your Argo CD custom resource contains at least one cluster namespace, the Operator now enables `tokenRef` strict mode. Secrets referenced by the SCM Provider and Pull Request generators through `tokenRef` have to carry this label:

[source,yaml]
----
metadata:
  labels:
    argocd.argoproj.io/secret-type: scm-creds
----

Label those secrets before upgrading:

[source,bash]
----
oc label secret <secret_name> -n <namespace> \
  argocd.argoproj.io/secret-type=scm-creds
----

There is a switch to turn strict mode off, `applicationsetcontroller.enable.tokenref.strict.mode: "false"` under `spec.cmdParams`, but it is explicitly not recommended for production. Treat it as a bridge.

TIP: This affects only the SCM Provider and Pull Request generators. If your ApplicationSets use Git, List, Cluster or Matrix generators without an SCM token, nothing changes for you.

=== The ImageUpdater spec.namespace field was removed

Any `ImageUpdater` custom resource that still contains `spec.namespace` fails validation. The controller derives the namespace to search from `metadata.namespace` of the resource itself, which also means the resource has to live in the same namespace as the applications it manages. If you experimented with the Technology Preview, this is a two-line fix, but it is a hard failure rather than a warning.

== Deprecations, including the sharding question

=== Dynamic shard scaling is deprecated, sharding is not

Let me be precise about what is deprecated and what is not.

Still there is sharding of the application controller. You still run multiple controller replicas, every registered cluster is still assigned to exactly one shard, and the distribution algorithm is still configurable. The product documentation still has a chapter about sharding clusters across application controller replicas, and sharding is still the standard answer when one controller can no longer keep up with a fleet of clusters.

Deprecated is the dynamic shard scaling feature, including the field `.spec.controller.sharding.dynamicScalingEnabled`. That is the mechanism that scaled the number of shards up and down automatically between `minShards` and `maxShards` based on `clustersPerShard`. It never left Technology Preview, since the tracker lists it as TP since 1.10 with no GA release, and it is now on its way out.

The practical consequence is that you size your shards statically:

.Static sharding
[source,yaml]
----
apiVersion: argoproj.io/v1beta1
kind: ArgoCD
metadata:
  name: openshift-gitops
  namespace: openshift-gitops
spec:
  controller:
    sharding:
      enabled: true # <1>
      replicas: 3 # <2>
      algorithm: round-robin # <3>
----
<1> Sharding has to be enabled explicitly.
<2> The number of application controller replicas, which is the number of shards.
<3> The distribution algorithm. The custom resource validates this field against `legacy`, `round-robin` and `consistent-hashing`.

WARNING: `minShards`, `maxShards` and `clustersPerShard` only take effect together with dynamic scaling. If your Argo CD custom resource carries them, they are either doing nothing or they depend on a deprecated feature.

Check what your clusters actually have configured:

[source,bash]
----
oc get argocd -A \
  -o jsonpath='{range .items[*]}{.metadata.namespace}{"/"}{.metadata.name}{"\t"}{.spec.controller.sharding}{"\n"}{end}'
----

Note that the `round-robin` algorithm itself is still listed as a Technology Preview in the tracker, even though the field exists in the custom resource and validates. If you need a supported statement for a customer, check with support rather than assuming.

=== The logformat field becomes logFormat

The `applicationSet` and `notifications` components used a lowercase `logformat` field, while `server`, `repo-server` and `application-controller` used camelCase `logFormat`. That inconsistency is being cleaned up, so use `logFormat` everywhere. The lowercase variant still works for backward compatibility and might be removed in a future release.

[source,bash]
----
oc get argocd -A -o yaml | grep -n "logformat"
----

=== kube-rbac-proxy is no longer used

The Operator uses the `WithAuthenticationAndAuthorization` function from `controller-runtime` instead of the deprecated `kube-rbac-proxy` image, so the Operator deployment runs one container instead of two. There is nothing to do, but do not be surprised by the changed pod. This change also caused a metrics scraping regression in 1.21.0 that produced `targetDown` alerts, fixed in 1.21.1.

=== Keycloak-based authentication, a reminder

Not new in 1.21, but it keeps coming up. Since GitOps 1.18 there is no support for Keycloak-based authentication in the Operator. The alternatives are Dex, or a self-managed Red Hat Build of Keycloak instance that Argo CD uses through OIDC.

== Known issues worth knowing before you upgrade

*Kustomize 5.8.x namespace propagation.* The bundled Kustomize 5.8.0 and 5.8.1 contain an upstream issue that prevents namespace propagation for Helm-generated resources. If your applications rely on Kustomize to set `metadata.namespace` for resources generated from a Helm chart, those resources come out without a namespace and the sync fails with an `InvalidSpecError`. The documented workaround is to provide Kustomize v5.7.1 to the repo server through init containers and volumes, register it in the Argo CD custom resource, and select it per application:

.Registering an additional Kustomize version
[source,yaml]
----
spec:
  kustomizeVersions:
    - version: v5.7.1
      path: /custom-tools/kustomize_5_7_1 # <1>
----
<1> The path where the binary is available inside the repo server pod. You place it there with `spec.repo.initContainers`, `spec.repo.volumes` and `spec.repo.volumeMounts`.

Applications then select it with `kustomize.version: v5.7.1` in their source. This is relevant if you combine Helm and Kustomize, for example with the link:/gitopscollection/2024-10-13-using-post-renderer[post-renderer pattern from Ep.12].

*Redis HA replication failure.* In 1.21.0 the Redis configuration switched from `requirepass` to ACL file-based authentication, but the new template was missing the `masterauth` directive. With `ha.enabled: true` this breaks replication and, with it, the Argo CD UI. Instances with `ha.enabled: false` are unaffected. Fixed in 1.21.1.

*Image Updater goroutine leak.* With the Git write-back method under heavy load, the controller could leak goroutines until Git operations failed. Fixed in 1.21.1. On 1.21.0 the mitigations are a longer `IMAGE_UPDATER_INTERVAL`, a periodic restart of the deployment, or higher pod PID limits.

The pattern is obvious. Do not deploy 1.21.0. Three of the four issues above are fixed in z-streams, and at the time of writing 1.21.4 is the current one.

== A short upgrade checklist

Before you press the button on a cluster that matters:

. Label any `tokenRef` secrets used by SCM Provider or Pull Request generators with `argocd.argoproj.io/secret-type: scm-creds`.
. Remove `spec.namespace` from any `ImageUpdater` custom resource.
. Check your Argo CD custom resources for `dynamicScalingEnabled`, `minShards`, `maxShards` and `clustersPerShard`, and convert to a static shard count.
. Replace the lowercase `logformat` field with `logFormat`.
. If you use Helm charts rendered through Kustomize, test the namespace propagation issue on a non-production cluster first.
. If you run Redis in HA mode, go to 1.21.1 or later.
. Check the `argocd.argoproj.io/tracking-id` and `argocd.argoproj.io/installation-id` annotations on Operator-managed RoleBindings and ClusterRoleBindings. The Operator no longer copies annotations from the Argo CD custom resource, but existing resources that already carry them have to have the annotations removed, or the resources deleted so the Operator recreates them. Otherwise a central Argo CD instance may claim and prune them.
. Pick your z-stream deliberately and confirm it supports your OpenShift version.

== Summary

OpenShift GitOps 1.21 is a substantial release. Two features graduate to GA, the Image Updater and the CLI, one Technology Preview finally makes the Argo CD Agent adoptable for existing installations, and a handful of smaller changes remove manual steps that never belonged in a declarative setup.

The changes that will actually cost you time are the small ones: a label on an SCM secret, a field that no longer validates, and a sharding configuration that depends on a deprecated feature. None of them is difficult, but all of them are easy to miss, which is why they are worth a checklist.

And sharding has not gone anywhere. Only the automatic scaling of it has.
